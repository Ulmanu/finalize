# Design — add-command-transaction-layer

## Context

The command layer is the single mutation boundary for UI, sync, and automation. It must be
atomic, idempotent, account-scoped, and deterministic so retries and offline replays are safe.

## Requirements Driving the Design

- `Typed application commands`
- `Atomic command transaction`
- `Deterministic command errors`

## Architecture

- `crates/app/src/commands.rs`:
  - `Command` variants for todo lifecycle/metadata/schedule/deadline/reminder/move (later
    changes add project/area/heading/tag variants).
  - `CommandEnvelope { operation_id, account_id, issued_at, command }` with `operation_id`
    generated by the caller (UUIDv7) so retries reuse it.
  - `DomainEvent` (serde) describing what changed; `Projection` invalidation targets
    (`Inbox`, `Today`, `Upcoming`, `Anytime`, `Someday`, `Logbook`, `Trash`, `Deadlines`,
    `Repeating`, `AllProjects`, `LoggedProjects`, `Project(id)`, `Area(id)`).
  - `CommandError` (`Validation`, `NotFound`, `Conflict { expected, actual }`, `Storage`,
    `NotSupported`).
  - `UnitOfWork` trait: load/save account-scoped entities, look up a change record by
    operation id, append a change record, commit/rollback.
  - `UnitOfWorkFactory` + `CommandDispatcher::execute(envelope)`:
    1. replay check by operation id,
    2. load entity (account-scoped),
    3. apply domain transition,
    4. save with expected version,
    5. append `ChangeRecord { operation_id, sequence, entity_id, events }`,
    6. commit,
    7. return `CommandOutcome { events, invalidated, sequence, replayed }`.
  - `invalidations_for(&DomainEvent)` maps events to projections; this is the single source of
    projection invalidation.
- `crates/infra/src/commands.rs`: `PgUnitOfWork` — one SQL transaction covering entity upsert,
  change-log insert, and `sync_metadata.sequence` increment (`select ... for update`).
- `crates/testkit/src/commands.rs`: `MemoryDatabase` + `MemoryUnitOfWork` with version
  conflicts, operation-id dedup, sequence allocation, and failure injection.

## Data and Persistence

Reuses `entities`, `change_log`, and `sync_metadata` from change 05. Change records store the
events as JSONB; the per-account sequence increments inside the same transaction.

## Offline and Sync

Operation ids and change records are exactly what the sync protocol (change 50) needs: a
client can resend an operation id and receive the recorded outcome. Change records carry
enough information to reconstruct events for other devices.

## UI and Accessibility

No UI; adapters dispatch commands and re-render invalidated projections.

## Error Handling

Errors are typed and serializable; storage failures roll back the transaction. Conflicts carry
expected/actual versions so callers can reload and retry.

## Testing Strategy

- Dispatcher tests over the in-memory unit of work: create/complete/cancel/reopen/delete/
  restore/move/schedule/deadline/reminder, event and invalidation assertions.
- Idempotent replay test (same operation id, no extra change record).
- Version conflict test.
- Account isolation test (foreign entity → not found, nothing persisted).
- Failure injection test (save failure → no change record, entity unchanged).
- Conditional PostgreSQL unit-of-work test (skipped without `DATABASE_URL`).

## Rollout / Migration

No schema change.

## Open Questions Resolved From the Repository

- **Who owns transactions**: the `UnitOfWork` port owns them; the dispatcher only orchestrates,
  so adapters decide SQL transaction scope.
- **Event storage**: events are stored as JSONB in `change_log.payload`, which doubles as the
  sync change feed.
